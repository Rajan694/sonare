# Deployment

How Sonare runs in production and how a change gets there.

```
Android / Linux / Windows apps ──┐                         ┌─► Neon Postgres (Singapore)
web: sonare.vip (Render static) ─┼─► api.sonare.vip ───────┼─► Render Key Value (cache)
                                 │   (Render, Docker, free) ├─► Resend (account email)
                                 │                          └─► Piped at home, through Tailscale
                                 │                              Funnel (key-checked gate)
GitHub Releases ◄── tag vX.Y.Z ──┘ (apps' downloads and update check)
```

| Piece                 | Where                                   | Defined in                                   |
| --------------------- | --------------------------------------- | -------------------------------------------- |
| API `sonare-api`      | Render web service, Docker, free plan   | `render.yaml`, `sonare-backend/Dockerfile`   |
| Web `sonare-web`      | Render static site (CDN), free          | `render.yaml`                                |
| Cache `sonare-cache`  | Render Key Value, free (memory only)    | `render.yaml`                                |
| Database              | Neon project `sonare`, branch `production` | migrations run on every API start        |
| Piped                 | this machine, Docker + Tailscale Funnel | `sonare-piped-backend/funnel.sh` (`.ps1`)    |
| App builds            | GitHub Releases of `Rajan694/sonare`    | `.github/workflows/release.yml`              |

## How a change reaches production

1. Work on `generic-branch` and push. CI runs in each repo (tests, lint, types, builds).
2. Open a pull request `generic-branch` → `main` in the repo that changed, and merge it once
   CI is green.
3. Render deploys `main` **after that commit's GitHub checks pass** (`autoDeployTrigger:
   checksPass`): the API when `sonare-backend` changes, the web app when
   `sonare-frontend/desktop` or `shared` change. The API applies new migrations as it starts.
4. Bump the submodule pointers in this root repo and push it.

App releases are separate: see [Releasing the apps](#releasing-the-apps).

## One-time setup

### 1. Neon (done 2026-10-12)

Project `sonare` (`flat-recipe-40204431`, org `org-patient-leaf-94637819`), branch
`production`, region `aws-ap-southeast-1`, Postgres 18, database `neondb`. All migrations are
applied. The root repo is linked (`.neon`, git-ignored) and Claude Code has the Neon MCP server
and the `neon` / `neon-postgres` skills.

The pooled connection string for Render:

```bash
neon connection-string production --pooled
```

### 2. Render Blueprint

1. Merge `generic-branch` into `main` in `sonare-backend`, `sonare-frontend` and this repo (Render
   deploys `main` and reads `render.yaml` from this repo's `main`).
2. In Render: **New → Blueprint**, connect GitHub, and give Render access to `Rajan694/sonare`,
   `Rajan694/sonare-backend` and `Rajan694/sonare-frontend`. Pick `Rajan694/sonare`; Render reads
   `render.yaml`.
3. Render asks for the values that aren't in the file:

   | Variable         | Value                                                                    |
   | ---------------- | ------------------------------------------------------------------------ |
   | `DATABASE_URL`   | the pooled Neon string above                                             |
   | `RESEND_API_KEY` | the `re_…` key (the one in `sonare-backend/.env`)                        |
   | `PIPED_KEY`      | `PIPED_KEY` from `sonare-piped-backend/.env`                             |
   | `GITHUB_TOKEN`   | optional: a fine-grained token with no permissions (lifts GitHub's 60 calls/hour on Render's shared IPs); leave empty otherwise |

   `JWT_SECRET` is generated by Render. Click **Apply**.
4. When the first deploy is live, check `https://sonare-api.onrender.com/api/v1/healthz`
   (`db`, `redis` and `piped` should be true) and open `https://sonare-web.onrender.com`.

### 3. DNS at Dynadot

In Render, each service's **Settings → Custom Domains** shows the target. At Dynadot (Domain
List → sonare.vip → DNS Settings):

| Host  | Type  | Value                                         |
| ----- | ----- | --------------------------------------------- |
| `@`   | A     | the IP Render shows for `sonare.vip`          |
| `www` | CNAME | `sonare-web.onrender.com` (redirects to `sonare.vip`) |
| `api` | CNAME | `sonare-api.onrender.com`                     |

Remove any AAAA records for these names (they block Render's certificates). Render issues the
TLS certificates once the records resolve; then **Verify** in Render.

### 4. Email (Resend)

In Resend, **Domains → Add Domain → sonare.vip**, then add the DNS records it lists (an MX and
TXT on `send`, the `resend._domainkey` TXT) at Dynadot and press **Verify**. Until it is
verified, Resend refuses to send from `no-reply@sonare.vip` and verification / reset emails fail
(the API logs `verification email failed`).

### 5. The admin account

The migrations create `admin@sonare.dev` with the development password. Sign in at
`https://sonare.vip/admin` right after the first deploy and change it under **Account**.

### 6. Piped at home

Piped has to be up for the web app and for the apps' fallback:

```bash
./update.sh prod                 # pull, start Piped, republish it with Funnel
loginctl enable-linger "$USER"   # keep Tailscale running after you log out
```

On Windows it's `.\update.ps1 prod` (Funnel through `funnel.ps1` and the Tailscale app). Every
5 minutes a timer (a scheduled task on Windows) checks each Funnel relay address and restarts
Tailscale if one stops answering; see `sonare-piped-backend/README.md`.

`PIPED_API_URL` in `render.yaml` is `https://sonare-piped.tailb61775.ts.net`; change it there
if the Funnel name ever changes.

### 7. Release signing secrets

In `Rajan694/sonare` → **Settings → Secrets and variables → Actions**, add:

| Secret                         | Value                                                     |
| ------------------------------ | --------------------------------------------------------- |
| `ANDROID_KEYSTORE_BASE64`      | output of `base64 -w0 ~/.gradle/sonare-upload.keystore`   |
| `SONARE_UPLOAD_STORE_PASSWORD` | from `~/.gradle/gradle.properties`                        |
| `SONARE_UPLOAD_KEY_ALIAS`      | from `~/.gradle/gradle.properties` (`sonare`)             |
| `SONARE_UPLOAD_KEY_PASSWORD`   | from `~/.gradle/gradle.properties`                        |

Keep a copy of the keystore somewhere safe: every Android update must be signed with it.

## Releasing the apps

1. Make sure the submodule pointers in this repo point at the frontend commit to release
   (normally `main` after a merge), and push.
2. Tag and push:

   ```bash
   git tag v1.2.0
   git push origin v1.2.0
   ```

3. The **Release** workflow builds the APK, the Linux AppImage / .deb / .tar.gz and the Windows
   .exe at that version and publishes the GitHub release with them. The intro page's download
   buttons and the apps' update check pick it up within 10 minutes (the API caches the list).

Versions come from the tag and nothing is committed back. Android's `versionCode` follows from
the version (1.2.0 → 1002000), so local `./build.sh` builds and CI builds of a version agree;
always release a higher version than the last one.

## Free-plan limits to keep in mind

- The API sleeps after 15 minutes without traffic; the first request then takes 30–60 s. The
  Android and desktop apps fetch YouTube themselves, so mostly the web app and sign-in feel it.
  Upgrading `sonare-api` to `starter` in `render.yaml` removes the sleep.
- Key Value keeps everything in memory only; a restart empties the cache, which is fine.
- Neon suspends the database after a few idle minutes; the first query then takes ~0.5 s. Free
  storage is 0.5 GB.
- Render's free plan blocks outbound SMTP, which is why mail goes through Resend's HTTP API.

## Checks after a deploy

- `https://api.sonare.vip/api/v1/healthz` → `ok: true`.
- `https://sonare.vip` shows the intro page; **Open web app** plays a song.
- Sign-up sends the verification email (check Resend's **Emails** log).
- Login rate limits key on the client IP: `TRUST_PROXY=1` assumes one proxy (Render's load
  balancer). If every user seems to share one limit, raise it in `render.yaml`.
